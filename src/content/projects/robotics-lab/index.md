## 

综述

一个长期维护、完全容器化的具身智能个人研究项目。起点是复现 NVIDIA Isaac Lab-Arena × GR00T N1.6 的 Unitree G1 移动操作 demo，后续会加入 ROS、控制核心和其他算法，实现全栈闭环。项目将使用纯仿真环境，也可能会调整机械结构。实现一套完整的embodied AI管线，让离线机器人自主感知环境、生成指令、执行动作，并从仿真逐渐向实际落地靠拢。开放式推进，终点不预设。

开发环境：

| 项 | 内容 |
| --- | --- |
| 主机 | Ubuntu 24.04 desktop，RTX 4080 Laptop |
| 容器 | Docker Compose 编排；VS Code Dev Containers 分别进入三个容器 |
| dev 镜像（约 5.4 GB） | UUbuntu 24.04、ROS 2 Jazzy、Clang 20 / C++26、ros2_control、MuJoCo、MoveIt 2、Nav2 |
| sim 镜像（约 44 GB） | Isaac Sim 6.0、Isaac Lab、Isaac Lab-Arena 0.3、RSL-RL，Python 3.12 |
| policy 镜像（约 26 GB） | GR00T N1.6、PyTorch 2.7、FlashAttention、DeepSpeed，Python 3.10 |

管线全容器化，三个独立的闭环容器。由于 GR00T N1.6 不涉及真机，目前dev不进入管线，由sim和policy交互。但后续研究中dev会承担确定性的控制工作。

| 容器 | 内容 | 定位 |
| --- | --- | --- |
| dev | ROS 2 通信、控制框架（ros2_control）、运动规划（MoveIt 2）、导航（Nav2）、MuJoCo 控制实验、C++ / Python 开发 | ROS适配层和控制核心 |
| sim | 物理仿真、环境和RL训练、闭环评估 | RL模型工作区。管线入口，向 policy 请求动作 |
| policy | LLM推理、微调、训练 | 高层LLM工作区，返回动作块 |

#### 设计上有三条约定：

1. 每个容器自己就是一个闭环。 不依赖另外两个也能单独运行和自检，因此可以单独拿到别的项目里复用。
2. 容器之间只通过数据交互：共享的模型与数据目录、运行记录目录，以及网络端点。目前唯一的跨容器通信，是 sim 通过本机网络向 policy 请求动作块。
3. 依赖互不污染。 GR00T 需要 Python 3.10，Isaac 需要 Python 3.12，各自的 PyTorch 和 CUDA 版本也不同；分开放就不用互相迁就。显卡不够时，policy 还可以整个搬到云端。

##  研究思路

_记录一些创新思路以供二次开发的方向。它们会在未来实施。_

**持续学习能力**  
机器人在部署到真实环境中必须能持续学习，而不是只靠仿真训练出一个固化的模型。但学习越自由，安全越不能交给学习来保证。
这个项目长期要回答问题之一是：怎样让机器人一边在真实世界里学习，一边始终守住物理安全。

**垂直领域机器人**
一个机器人不应该、也不可能同时应付所有场景，尝试打造一个在所有物理场景中精准的AI智能体技术上错误、经济上也不现实。
在具体场景里，它的目标是一贯的、有限的，所需的能力可以显式列出来：例如，必须会抓握、必须会行走、必须会采摘苹果。不同场景的重点也完全不同：家庭机器人要面对细碎复杂的环境、人机交互和情绪价值；农业机器人要面对泥土、天气带来的随机性，摘水果和收小麦是两种完全不同的能力；医疗机器人需要绝对的安全和保守，还要真正理解目标，比如"清理血栓"是把堵住的地方疏通，而不是字面意义上的清空。

### 原则

1. AI 不进入控制管线。 AI 只负责决定"做什么"，并把决策编排成各部件的指令。真正驱动电机的控制回路是确定性的，以高速周期持续运行，不等 AI 推理。
2. 决策要经过审议。 多个 AI 专家、云端模型或人类共同判定一个决策是否合理。"无视前方的儿童继续前进"这样的决策会被否决，并受到严厉惩罚。
3. 物理安全由确定性的门阀推演。 比如计算机器人离摔倒还差多少：如果某个动作会让一个很小的意外外力就能把它推倒，这个动作就被否决。被否决的动作不执行，确定性逻辑立刻接管。
4. 学习在真实环境中持续进行，除非显式固化。 奖励由人来设计，审议和门阀的否决也是学习信号。
5. 用固定的能力集锚定机器人。 它要时时用这套能力自检，防止在学习过程中忘掉已有的本领或漂移。

### 架构设想

现在复现的 demo 并不符合上面的原则：大模型直接给出关节目标，腿部行走也由强化学习网络在控制回路里生成。之后我会按自己的架构二次开发：

决策层：只关注感知自身和环境，决定是否发布决策、发布何种决策。能力集显式固定，每个 AI 专家负责一项能力，由调用者把需求分发；专家可以热插拔。
审议层：跳出机器人本位，从环境和风险的角度判断**决策**是否合理，给出奖惩，让机器人的行为不产生偏移。
编排层：掌握硬件知识库的专家 AI 负责组合能力，把决策变成对各部件的确定性 API 调用。
安全门阀：对每个 API 调用推演物理后果并审计。
控制核心：确定性、高频地执行，不受 AI 推理延迟影响；各能力之间的动力学耦合也在这里处理。

_到那时，正在复现的 GR00T 基线就是对照组：在同一个任务上，比较安全违规次数、新增能力后其他能力是否退化，以及环境变化后适应得多快。在接触真机之前，这些都可以先在仿真里刻意改变物理参数来做。_
